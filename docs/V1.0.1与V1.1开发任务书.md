## 3. 全阶段共同要求

### 3.1 技术与架构

- 继续使用仓库现有的原生微信小程序、TypeScript、WXML、WXSS 和微信本地 Storage。
- 不引入跨端框架、UI 组件库、云开发、数据库或后端服务。
- 页面不得直接分散调用 `wx.getStorageSync` 或 `wx.setStorageSync` 操作课表数据；读取、写入、备份和迁移必须由服务层统一负责。
- JSON 必须使用 `JSON.parse` 和 `JSON.stringify` 处理，禁止使用 `eval`、`Function` 或其他执行字符串代码的方式。
- 所有导入和迁移都必须遵守“先完整读取与校验、再一次性写入”的原则，不能边校验边覆盖现有数据。
- 用户取消、输入无效、版本不兼容或写入失败时，原有课表数据不得改变。
- 新增交互应保持现有视觉风格，并保证窄屏可用、文字清晰、按钮有明确名称和选中状态。

### 3.2 数据安全

- 不得只修改 `schemaVersion` 数字而不完成对应字段转换。
- 不得静默删除无法识别的课程、学期或周次数据。
- 发生不可恢复的数据错误时，应停止写入、保留原数据并向用户说明原因。
- 数据迁移与覆盖恢复前必须先保存一份原始数据快照。
- 任何自动修复、过滤或跳过行为都必须在预览或结果提示中说明数量和原因。

### 3.3 文档

每个版本的 Pull Request 都必须同步更新：

- `README.md`：只写该 PR 已经实现并验证的用户功能、页面入口和使用方式。
- `CHANGELOG.md`：按 V1.0.1、V1.1 分别记录已完成的变化。
- 如果最终实现改变了本任务书中约定的数据结构或交互，Liu 必须先说明原因并取得 Yebin 确认，再同步修改相关设计说明。

## 4. 里程碑一：V1.0.1 数据备份与恢复

### 4.1 用户目标

用户能够把当前本地课表导出为可复制保存的 JSON 文本，并在同一设备或其他设备中恢复。恢复前可以看见数据内容与风险，操作失败不会损坏现有课表。

### 4.2 页面与入口

- 新增“数据管理”页面，并从课表主页提供清晰入口。
- 页面至少提供以下功能：
  - 导出课表。
  - 粘贴并解析备份 JSON。
  - 查看导入预览。
  - 覆盖现有课表。
  - 合并到现有课表。
  - 查看并恢复最近一次自动备份。
- V1.0.1 使用“复制 JSON 到剪贴板、从输入框粘贴 JSON”的方式完成导入导出，不做系统文件选择器、CSV、Excel、图片或教务系统导入。
- 覆盖、合并和恢复最近备份都需要二次确认；确认文案必须说明会发生什么变化。

### 4.3 备份格式

备份文件使用独立的外层封装，不把应用备份格式与内部 Storage 版本混为一谈。建议结构如下；字段名称可以在评审前提出调整，但语义不得减少：

```ts
interface TimetableBackupEnvelope {
  app: 'qige-timetable'
  backupVersion: 1
  exportedAt: string // ISO 8601 时间字符串
  data: TimetableStorage
}
```

要求：

- `app` 用于识别是不是本项目生成的备份。
- `backupVersion` 表示外层备份格式版本。
- `exportedAt` 必须是有效的 ISO 8601 时间字符串。
- `data.schemaVersion` 表示内部课表数据版本。
- V1.0.1 导出当前 `schemaVersion: 1` 数据，不得提前伪装成 V2。
- JSON 输出需要稳定、完整，不包含最近备份、个人配置、日志、密钥或其他无关 Storage 数据。
- 单次粘贴内容上限设为 1 MiB；超过后停止解析并给出明确提示。

### 4.4 导入校验

导入写入前必须完成以下校验：

- JSON 语法有效。
- 根对象、`app`、`backupVersion`、`exportedAt` 和 `data` 存在且类型正确。
- 当前版本只接受明确支持的备份版本和 Storage 版本；更高未知版本必须拒绝，不能猜测转换。
- `courses` 必须是数组。
- 每门课程的 ID、名称、星期、开始节次、结束节次、颜色和时间戳合法。
- 星期只能为 1–7，节次只能为 1–9，开始节次不能晚于结束节次。
- 备份内部不能存在同一天、重叠节次的冲突课程。
- 不得因为部分课程合法就静默导入；只要存在结构或字段错误，应阻止整个导入并显示具体原因。

### 4.5 导入预览

解析成功后不能立即写入，必须先显示预览，至少包括：

- 备份导出时间。
- 内部数据版本。
- 备份中的课程总数。
- 当前课表课程总数。
- 重复课程数量。
- 与当前课表冲突的课程数量。
- 选择“覆盖”后的预计课程数。
- 选择“合并”后的预计新增、跳过和最终课程数。

课程 ID 相同，或者课程名称去除首尾空格后相同且星期、开始节次、结束节次相同，视为重复课程。重复与冲突必须分别统计，不能用同一个模糊提示代替。

### 4.6 覆盖与合并规则

**覆盖现有课表：**

- 备份本身通过全部校验后，使用备份中的课程整体替换当前课程。
- 覆盖前先把当前完整 Storage 根数据写入单独的“最近自动备份”Storage key。
- 自动备份成功后才能写入导入数据。
- 写入失败时保留自动备份，恢复原数据，并显示失败提示。

**合并到现有课表：**

- 不修改现有课程。
- 重复课程默认跳过。
- 与现有课程发生时间冲突的导入课程默认跳过，并在预览和结果中列出原因。
- 只把既不重复也不冲突的课程加入当前课表。
- 合并也必须先生成最近自动备份，再一次性写入最终结果。
- 合并结束后明确提示新增、跳过重复、跳过冲突和最终课程数量。

### 4.7 最近自动备份

- 只需保留最近一份覆盖或合并前的自动备份，不做多版本历史列表。
- 数据管理页面应显示最近备份的生成时间、数据版本和课程数量。
- 恢复最近备份前需要预览并二次确认。
- 没有最近备份时，页面显示明确的空状态，不显示不可用的伪入口。

### 4.8 迁移框架

V1.0.1 需要建立统一的版本判断和迁移入口，为 V1.1 使用，但本版本不执行 V1 到 V2 的实际字段迁移。

- 读取数据时先识别 `schemaVersion`。
- 当前 V1.0.1 只正常读写 V1。
- 未知更高版本不得被降级写回。
- 迁移函数必须能在内存中生成候选结果，校验通过后再持久化。
- 页面不负责判断或修改数据版本。

### 4.9 建议模块范围

Liu 可以根据现有结构确定最终文件名，但职责需要保持清晰：

- 数据管理页面。
- 统一备份服务。
- 统一存储快照、恢复和原子写入能力。
- 备份格式及校验类型。
- 数据版本识别与迁移入口。
- 课表主页的数据管理入口。
- 页面路由、README 和 CHANGELOG。

不应借此 PR 重写课表网格、课程编辑页或全局样式。

## 5. 里程碑二：V1.1 学期与教学周

### 5.1 开始条件

只有满足以下条件后才能开始 V1.1：

1. V1.0.1 Pull Request 已由 Yebin 审核并合并到 `main`。
2. Liu 本地 `main` 已通过 `git pull --ff-only` 更新到最新提交。
3. V1.0.1 的备份、覆盖、合并和最近自动备份功能仍能正常使用。

### 5.2 用户目标

用户可以设置当前学期，根据日期查看当前教学周，并为课程设置全部周、单周、双周或指定周次。两门课程只有在星期、节次和实际上课周次都重叠时才算冲突。

### 5.3 学期设置

- 新增“学期设置”页面，并从课表主页提供清晰入口。
- 当前版本只管理一个当前学期，不做多学期历史列表。
- 学期至少包含第一教学周的星期一日期和学期总周数。
- 开始日期必须是有效的本地日历日期，并在界面中明确说明应选择“第一教学周的星期一”。
- 学期总周数必须是 1–30 的整数，界面可提供 16、18、20 等常用值。
- 日期计算必须按本地自然日处理，不能直接依赖可能产生 UTC 偏移的字符串解析方式。
- 修改学期设置前要预览会影响多少门课程，并二次确认。

### 5.4 当前周与周次浏览

- 从第一教学周星期一开始，每经过 7 个自然日增加一周。
- 当前日期早于学期开始日或晚于学期最后一天时，显示“当前不在教学周内”。
- 课表顶部显示当前查看的“第 N 周”。
- 支持查看上一周、下一周，并提供直接选择 1 到学期总周数的方式。
- 不得切换到小于 1 或大于学期总周数的周次。
- 当前日期在学期内时，首次进入默认查看当前教学周。
- 当前日期不在学期内时显示明确状态，但仍允许手动选择某一教学周查看。
- 课表和“今日安排”只显示当前所选周次实际有课的课程。

### 5.5 课程周次设置

课程编辑页增加全部周、单周、双周和指定周次四种设置。

- 指定周次至少选择一周，不能保存空周次数组。
- 所有周次必须在 1 到学期总周数之间。
- 最终实际周次数组必须去重并按升序保存。
- 编辑已有课程时必须正确回显原来的周次设置。
- 页面不能只依赖颜色表示已选状态，应同时使用勾选、文字或其他明确标记。
- 当学期总周数改变时，全部周、单周和双周课程根据新的总周数重新计算；指定周次课程只保留仍在新范围内的周次。
- 如果修改总周数会使指定周次课程变为空，必须阻止保存，并提示用户先处理受影响课程。

### 5.6 V2 数据结构

V1.1 将内部课表数据升级为 `schemaVersion: 2`。建议结构如下：

```ts
interface TermSettings {
  startDate: string // YYYY-MM-DD，第一教学周的星期一
  totalWeeks: number // 1..30
}

type WeekMode = 'all' | 'odd' | 'even' | 'custom'

interface CourseV2 extends CourseV1 {
  weekMode: WeekMode
  weeks: number[] // 实际上课周次，升序、去重、非空
}

interface TimetableStorageV2 {
  schemaVersion: 2
  term: TermSettings
  courses: CourseV2[]
}
```

- `weekMode` 用于正确回显用户选择，并在学期总周数变化时重新计算全部周、单双周。
- `weeks` 保存已经展开的实际上课周次，课表过滤和冲突判断统一使用该数组。
- `CourseV1` 指当前 `main` 中已有的课程字段，迁移时必须完整保留。
- 保存或迁移前必须校验 `weekMode` 与 `weeks` 一致。
- 如果 Liu 认为需要调整字段名称或避免继承写法，可以提出等价结构，但不能删减上述语义。

### 5.7 V1 到 V2 的迁移

检测到 `schemaVersion: 1` 时按以下顺序处理：

1. 完整读取 V1 原始数据，不立即写回。
2. 提示用户设置第一教学周星期一和学期总周数。
3. 用户确认后，先把完整 V1 数据保存为最近自动备份。
4. 将每门旧课程迁移为 `weekMode: 'all'`，并把 `weeks` 展开为 1 到学期总周数。
5. 在内存中校验完整 V2 结果，包括学期、课程字段、周次和课程冲突。
6. 全部通过后一次性写入 V2。
7. 写入后重新读取并确认结构有效，才显示迁移成功。

迁移过程中还必须满足：

- 保留课程 ID、名称、星期、节次、教师、教室、颜色、创建时间和更新时间。
- 用户取消学期设置时不修改 V1 数据；课表继续按原来的每周重复方式显示，但教学周功能保持不可用，并在下次进入时继续提供设置入口。
- 迁移校验或写入失败时保留 V1 原数据和自动备份，不得写入半成品 V2。
- 已是合法 V2 的数据不能重复迁移。
- 未知更高版本不能按 V1 或 V2 猜测处理，也不能降级覆盖。

### 5.8 周次冲突规则

课程冲突必须同时满足星期相同、节次区间重叠、`weeks` 至少有一个相同周次。

- 周一第 1–2 节单周课程与同时间双周课程不冲突。
- 周一第 1–2 节第 1–8 周课程，与周一第 2–3 节第 8–16 周课程在第 8 周冲突。
- 周一第 1–2 节第 1–4 周课程，与同时间第 5–8 周课程不冲突。
- 星期或节次不重叠时，无论周次如何都不冲突。

冲突提示至少显示星期、节次、冲突课程名称和重叠周次。重叠周次较多时可以压缩表示，但不能只显示“课程冲突”。

### 5.9 学期设置变更规则

- 修改开始日期不会改变课程周次数组，但会改变各教学周对应的自然日期；保存前需要明确提示。
- 修改总周数时，先在内存中计算所有课程的新周次，再展示受影响课程数量。
- 缩短学期时不得保留超出新范围的周次。
- 增加学期总周数时，`all`、`odd`、`even` 根据新范围重新展开；`custom` 不自动增加新周次。
- 只有所有课程调整后仍合法，才能一次性写入新的学期设置和课程数据。
- 修改前生成最近自动备份，失败时恢复原学期和原课程。

### 5.10 备份功能的 V2 兼容

- 新导出的备份包含完整 V2 学期和课程数据。
- V2 备份恢复后，学期设置、周次模式和实际上课周次必须保持一致。
- V1.1 仍需识别合法的 V1 备份；导入 V1 备份时先要求用户确认学期设置，再按迁移流程生成 V2。
- V2 应拒绝未知更高版本，不得把未知字段静默降级覆盖。
- 覆盖、合并和迁移前仍需生成最近自动备份。
- 合并 V1 或 V2 数据时，重复和冲突判断使用目标 V2 的周次规则。

## 7. 分支与提交规则

### 7.1 V1.0.1 分支

```powershell
git switch main
git pull --ff-only
git switch -c feature/v1-0-1-data-backup
```

完成并检查后推送该分支：

```powershell
git push -u origin feature/v1-0-1-data-backup
```

Pull Request 目标分支为 `main`，标题建议使用 `feat: 完成 V1.0.1 数据备份与恢复`。

只在该分支提交 V1.0.1。建议按可独立说明的内容拆分提交，例如：

```text
feat: 增加课表数据导出与导入预览
feat: 增加覆盖合并与最近自动备份
test: 补充课表备份恢复验证
docs: 更新数据管理使用说明
```

### 7.2 V1.1 分支

V1.0.1 合并后，从更新后的 `main` 创建：

```powershell
git switch main
git pull --ff-only
git switch -c feature/v1-1-term-weeks
```

完成并检查后推送该分支：

```powershell
git push -u origin feature/v1-1-term-weeks
```

Pull Request 目标分支为 `main`，标题建议使用 `feat: 完成 V1.1 学期与教学周支持`。

只在该分支提交 V1.1。建议提交示例：

```text
feat: 增加学期设置与教学周计算
feat: 增加课程周次选择和课表过滤
feat: 升级课表数据并迁移旧课程
fix: 按实际上课周次判断课程冲突
test: 补充教学周与数据迁移验证
docs: 更新教学周功能说明
```

### 7.3 两个分支共同规则

- 不直接向 `main` 推送代码。
- 一个分支只包含对应里程碑，不把 V1.1 提前混入 V1.0.1。
- 不使用 `git add .` 或 `git add -A`；只暂存已检查的明确路径。
- 提交前必须执行 `git status --short`、查看实际差异，并执行 `git diff --staged --check`。
- 每个提交只表达一个清晰目的，不使用“更新”“修改一下”“最终版”等模糊提交信息。
- 不强制推送，不改写共享分支历史，不删除或覆盖不属于本任务的改动。
- 不提交 `project.private.config.json`、`node_modules/`、`miniprogram_npm/`、编辑器配置、日志、密钥、二维码或个人资料。
- 如果需要新增依赖，必须先说明用途、维护情况和不使用依赖的替代方案，经 Yebin 确认后再加入。
- 公共数据模型、存储服务、`app.json`、`package.json` 和 `package-lock.json` 属于容易冲突的文件，修改前确认分支基于最新 `main`。
- 每个 PR 都应保持可独立编译和验收，不能依赖尚未合并的另一个功能分支。

## 8. Pull Request 提交规则

### 8.1 PR 顺序与合并

1. 先推送 `feature/v1-0-1-data-backup`，创建 V1.0.1 PR。
2. Liu 完成自测和说明后等待 Yebin 审核，不自行合并。
3. 审核意见处理完毕，由 Yebin 决定是否使用 Squash merge 合并。
4. V1.0.1 合并后，再创建并推送 `feature/v1-1-term-weeks`。
5. V1.1 使用第二个独立 PR，重复审核与验收流程。

### 8.2 每个 PR 必须提供的内容

- 本次版本目标和实际完成范围。
- 修改过的页面、服务、模型、工具和文档。
- Storage 修改前后的结构示例。
- 导入、覆盖、合并或迁移过程中如何保证原数据安全。
- 对应验收清单的逐项测试结果，未测试项必须明确标为未测试。
- 微信开发者工具编译结果和 Console 状态。
- 手机预览结果；如果未完成，必须明确说明，不能填写为通过。
- 新增或修改界面的截图或录屏。
- 是否增加依赖；如有，说明原因。
- README、CHANGELOG 和设计说明是否同步。
- 已知问题、暂未覆盖的边界和需要审核者重点检查的风险。

### 8.3 V1.0.1 PR 额外证据

- 一份经过脱敏的导出 JSON 示例，不包含真实课程、个人信息或密钥。
- 有效导入、无效 JSON、未知版本、覆盖、合并、重复、冲突和最近备份恢复的测试结果。
- 覆盖或合并失败后原数据仍然存在的证明。

### 8.4 V1.1 PR 额外证据

- V1 与 V2 Storage 的脱敏示例。
- 至少一组真实执行的 V1 到 V2 迁移结果，包括迁移前后课程数量和字段保留情况。
- 单周与双周同一时间不冲突、存在共同周次时冲突的测试结果。
- 学期开始前、第一周、周次边界、最后一周和学期结束后的计算结果。
- V2 备份导出和恢复、V1 备份导入并迁移的测试结果。
