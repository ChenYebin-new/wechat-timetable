# 微信课表小程序协作开发规范

> 适用项目：微信课表小程序
> 文档版本：1.0
> 更新日期：2026-09-05

## 1. 协作目标

本项目使用 GitHub 管理代码和开发任务。所有改动通过独立分支和 Pull Request 合并，`main` 分支始终保留已经检查、可以继续测试的代码。

第一版使用原生微信小程序、TypeScript 和微信本地 Storage。开发工具以微信开发者工具为准，代码可以使用 PyCharm 或其他编辑器编写。

## 2. 成员职责

### 仓库管理员

- 管理 GitHub 成员权限和仓库设置。
- 维护 `main` 分支及合并规则。
- 检查 Pull Request 并安排代码审核。
- 处理版本标签和紧急问题。

### 功能开发者

- 按任务范围创建分支和修改代码。
- 在提交前完成本地编译和基本测试。
- 发起 Pull Request，说明改动内容和测试结果。
- 根据审核意见继续修改。

### 发布负责人

- 从指定的 `main` 提交生成微信开发版本。
- 完成预览、真机测试和体验版检查。
- 在微信公众平台上传、提交审核和发布版本。
- 记录微信版本号对应的 Git 提交编号。

### 测试成员

- 使用体验版二维码测试。
- 反馈设备型号、操作步骤、预期结果和实际结果。
- 提供必要的截图或录屏。

GitHub 仓库权限和微信小程序后台权限分别管理。获得 GitHub 仓库权限，不代表已经获得微信开发者或体验成员权限。

## 3. 仓库基本规则

- 仓库默认为私有仓库。
- 默认分支为 `main`。
- 不直接向 `main` 推送代码。
- 每项功能、修复或文档更新使用单独分支。
- 合并方式统一使用 Squash merge。
- Pull Request 合并后删除对应分支。
- 不使用 `git add .` 或 `git add -A` 批量暂存未检查的文件。
- 不使用强制推送改写共享分支历史。
- 不提交与当前任务无关的格式化、重命名或清理改动。

空仓库第一次建立项目基线时，可以由仓库管理员直接创建并推送 `main`。首次提交完成后，所有功能、修复和文档更新都必须改用独立分支和 Pull Request。

## 4. 分支命名

分支名使用小写英文，单词之间用短横线连接。

```text
feature/timetable-grid       新功能
feature/course-editor        新功能
fix/course-overlap           问题修复
refactor/course-storage      代码整理
test/storage-service         测试
docs/update-release-guide    文档
chore/update-tooling         工程维护
```

一个分支只处理一项任务。不要在同一分支混合多个无关功能。

## 5. 开始开发

首次参与项目时，克隆仓库并安装项目需要的依赖：

```powershell
git clone <仓库地址>
cd <项目目录>
cd wechat-timetable
npm install
```

开始新任务前，先同步 `main`，再创建自己的分支：

```powershell
git switch main
git pull --ff-only
git switch -c feature/course-editor
```

不要在已经落后很久的分支上直接继续开发。如果任务范围不清楚，先确认需要修改的页面、模块和验收条件。

## 6. 提交代码

提交前先检查改动范围：

```powershell
git status --short
git diff
```

只暂存本次任务涉及的文件：

```powershell
git add -- wechat-timetable/miniprogram/pages/course-edit
git add -- README.md CHANGELOG.md
```

再次确认已暂存内容：

```powershell
git diff --staged
git diff --staged --check
```

提交信息使用下面的格式：

```text
feat: 增加课程编辑页面
fix: 修复连续课程卡片高度错误
refactor: 整理课程本地存储逻辑
test: 增加课程冲突校验测试
docs: 补充真机测试步骤
chore: 更新开发依赖
```

每个提交只包含一个完整、可说明的改动。不要使用 `update`、`修改一下`、`最终版` 这类无法看出内容的提交信息。

提交后将当前分支推送到 GitHub：

```powershell
git push -u origin feature/course-editor
```

## 7. Pull Request 规则

开发者不能把未审核的功能直接合并进 `main`。完成任务后，在 GitHub 创建 Pull Request。

Pull Request 说明必须包含：

1. 本次解决的问题。
2. 主要改动和涉及的页面或模块。
3. 实际测试过的操作路径。
4. 微信开发者工具是否编译通过。
5. 是否完成手机预览或真机测试。
6. UI 改动的截图或录屏。
7. 是否修改了本地存储的数据结构。
8. 是否更新 README 和 CHANGELOG。
9. 尚未解决的问题或已知限制。

建议使用下面的格式：

```markdown
## 改动内容

- （填写具体改动）

## 测试结果

- [ ] 微信开发者工具编译通过
- [ ] Console 没有新增错误
- [ ] 已测试主要操作路径
- [ ] 已完成手机预览
- [ ] 已检查敏感信息
- [ ] 已按需更新 README 和 CHANGELOG

## 截图或录屏

在此处添加。

## 补充说明

填写已知问题、未覆盖范围或需要审核者关注的内容。
```

审核者应检查实际代码和测试结果。只有评论已经处理、检查通过后，才能使用 Squash merge 合并。

Pull Request 作者不能把自己的审核当作独立审核。条件允许时，至少由一名没有编写该改动的成员确认。

## 8. 测试要求

每次提交 Pull Request 前，至少完成以下检查：

- 微信开发者工具能够正常编译。
- Console 没有新增报错。
- 本次修改涉及的页面能够正常打开。
- 新增、编辑和删除课程正常。
- 课程时间冲突能够被正确拦截。
- 修改后关闭并重新进入小程序，数据仍能读取。
- UI 改动至少完成一次手机预览。

准备上传微信版本前，还要检查：

- iPhone 和 Android 均完成真机测试。
- 窄屏设备没有严重遮挡或文字过小问题。
- 空课表、课程较多、周日课程和连续多节课程显示正常。
- 输入时键盘不会挡住主要表单操作。
- 删除本地数据后，小程序可以正常首次启动。
- 体验版没有测试文字、调试按钮或未完成功能入口。

微信本地 Storage 不会通过 GitHub 同步。不同成员和不同手机上的课程测试数据彼此独立。

## 9. 容易冲突的文件

以下文件应指定负责人，或在修改前通知其他成员：

- `wechat-timetable/miniprogram/app.json`
- `wechat-timetable/miniprogram/app.wxss`
- `wechat-timetable/project.config.json`
- `wechat-timetable/package.json`
- `wechat-timetable/package-lock.json`
- 公共数据模型和存储服务

不要为了减少冲突而覆盖别人的文件。发生冲突时，先保留双方改动，确认业务意图后再解决。

自己的功能分支需要同步最新代码时，建议把远程 `main` 合并进当前分支：

```powershell
git fetch origin
git merge origin/main
```

解决冲突后重新执行编译和相关测试。除非团队已经明确同意，不要对共享分支执行 rebase 后强制推送。

## 10. 敏感信息和本地配置

下面的内容不能提交到 GitHub，也不能放进 Issue、Pull Request、截图或聊天记录：

- AppSecret。
- 微信代码上传私钥。
- Access Token 和云开发密钥。
- 管理员二维码、登录凭证和备案材料。
- 与开发无关的手机号、邮箱、住址或身份信息。

`project.config.json` 用于保存团队共享的项目设置，可以提交。`project.private.config.json` 保存个人开发工具设置，不提交。

项目的 `.gitignore` 至少应包含：

```gitignore
project.private.config.json
node_modules/
miniprogram_npm/
.idea/
.vscode/
*.log
.env
.env.*
!.env.example
private.*.key
upload_private.key
*.pem
```

提交前必须检查待提交文件。如果发现密钥已经进入 Git 历史，立即停止推送并通知仓库管理员。仅删除当前文件不能解决泄露问题，相关密钥还需要撤销或更换。

## 11. README 和更新记录

以下改动需要同步更新 README：

- 新增用户可见功能。
- 修改安装、启动或开发步骤。
- 增加或删除依赖。
- 改变项目目录结构。
- 修复会影响用户使用的重要问题。

用户可见改动还要写入 `CHANGELOG.md`。文档只记录已经实现并确认的内容，不提前宣传尚未完成的功能。

## 12. 微信版本发布

只有发布负责人可以上传和发布正式版本。其他开发者不要自行提交微信审核或覆盖开发版本。

发布流程如下：

```text
功能分支开发
→ Pull Request 审核
→ 合并到 main
→ 从 main 完成模拟器和真机测试
→ 上传微信开发版本
→ 设置体验版
→ 完成体验版验收
→ 提交微信审核
→ 审核通过后发布
→ 创建对应的 Git 标签
```

上传微信开发版本时，在备注中写明 Git 提交短编号：

```text
版本：0.1.0
备注：首个课表版本，Git commit abc1234
```

`main` 上存在某项代码，不代表该代码已经发布到微信。线上问题应先根据微信版本备注找到对应 Git 提交，再进行修复。

## 13. 禁止操作

- 直接向 `main` 推送未经审核的代码。
- 强制推送或擅自改写共享分支历史。
- 未经确认删除其他成员的代码或配置。
- 把无关修改混入当前 Pull Request。
- 提交密钥、账号凭证、个人资料或私有配置。
- 未经发布负责人同意上传、提交审核或发布微信版本。
- 在没有实际测试的情况下填写测试通过。
- 合并仍有未解决评论或明显报错的 Pull Request。

## 14. 完成任务后的操作

Pull Request 合并后，更新本地 `main` 并删除已完成的本地分支：

```powershell
git switch main
git pull --ff-only
git branch -d feature/course-editor
```

开始下一项任务时，从最新的 `main` 创建新分支，不继续复用已经合并的旧分支。

## 15. 提交前快速检查

```text
[ ] 当前分支不是 main
[ ] 改动只属于当前任务
[ ] 已查看 git diff
[ ] 只暂存了明确文件
[ ] 微信开发者工具编译通过
[ ] 相关功能已经实际操作测试
[ ] 没有密钥和个人信息
[ ] README 和 CHANGELOG 已按需更新
[ ] Pull Request 写明测试结果和已知问题
```
